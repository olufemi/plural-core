# Plural Transaction Reversal Process - Assessment and Implementation Design

Last updated: 2026-07-20

## Executive summary

The current Plural reversal implementation has useful building blocks across transaction-service, fxpeer-service, utility-service, and backoffice-service. However, the reversal process must be hardened before pilot becomes production because a reversal is a money-moving operation and must never be triggered from an unconfirmed timeout, ambiguous provider response, or manual retry alone.

The governing control rule is:

> A reversal must only be executed after the system confirms that the original fulfilment genuinely failed, using the original end-to-end transaction reference and provider/downstream status evidence. A timeout, exception, or unreachable provider is not proof of failed fulfilment.

This document records the current implementation, gaps, proposed target architecture, and phased implementation plan.

## Current reversal flows

### 1. Transaction-service reversals

The transaction service tracks successful debit logs in `SuccessDebitLog`. When an external fulfilment path fails after the internal debit has succeeded, `NipBankService` can mark the debit for rollback.

Current states visible in `SuccessDebitLog` include:

- `NONE`
- `PENDING`
- `FAILED`
- `SUCCESS`
- `RECON_REQUIRED`

Automatic retry is handled by `WalletCreditRetryScheduler`. It finds logs marked for rollback and builds a credit request from the original debit payload. The rollback transaction id is generated by appending `-RB` to the original transaction id.

Backoffice/admin retry is exposed by `AdminReversalController` through:

- `GET /admin/reversals/summary`
- `GET /admin/reversals`
- `POST /admin/reversals/{transactionId}/retry`

`ReversalAdminService.retryCase` also builds the rollback credit request using the original debit payload and the same `originalTransactionId-RB` convention.

### 2. FxPeer airtime/VAS rollback

`ProcSochitelServices` performs the airtime flow by first posting internal buyer, seller, and GL legs. When provider fulfilment fails, it calls `AirtimeRollbackService.executeRollback`.

`AirtimeRollbackService` creates rollback leg records in `AirtimeRollbackLog`. Each leg has its own `legKey`, action type, user type, auth value, rollback transaction id, account number, amount, retry count, and status.

The retry scheduler picks up pending or failed rollback legs. Backoffice can also retry a specific airtime rollback case through FxPeer admin endpoints.

### 3. Backoffice reversal desk

Backoffice has a unified reversal desk through `BoReversalController`:

- `GET /backoffice/reversals/summary`
- `GET /backoffice/reversals/cases`
- `POST /backoffice/reversals/cases/{source}/{caseRef}/manual-request`

`ReversalExceptionService` aggregates cases from transaction-service and FxPeer airtime reversals. It can normalize cases into a common shape for backoffice.

Manual reversal requests are submitted into the backoffice approval engine. `ApprovalService` executes the downstream retry after approval.

### 4. Utility wallet credit/debit layer

Transaction-service and FxPeer eventually call utility-service credit/debit endpoints:

- `/walletmgt/account/debit-Wallet-phone`
- `/walletmgt/account/credit-Wallet-phone`

`FinWealthPaymentTransactionRepo` contains transaction lookup helpers such as `existsByTransactionId` and `findByTransactionId`. However, the reviewed credit/debit caller methods did not clearly enforce a pre-post idempotency check before calling the wallet/core credit or debit operation.

This means idempotency may exist deeper in the wallet system, but it is not sufficiently visible or guaranteed from the utility-service caller layer.

## Current gaps and risks

### Gap 1: Timeout can be confused with failure

The target rule is that a timeout or connection exception must not automatically trigger reversal. The current system has rollback marking paths, but the reviewed reversal retry paths do not consistently prove that provider fulfilment has been confirmed failed before reversal execution.

Risk: A transaction may be reversed even though the provider later completes or has already completed fulfilment.

### Gap 2: Reversal execution is not centrally gated by fulfilment confirmation

The system needs a clear pre-reversal gate:

- original debit exists
- original end-to-end transaction id exists
- provider/downstream reference exists where applicable
- provider status enquiry has been performed
- fulfilment is confirmed failed, or manual investigation has approved reversal

Current retry paths mostly focus on retrying rollback records already marked as pending or failed.

Risk: A wrongly marked case can become a money movement without enough evidence.

### Gap 3: Duplicate reversal/race risk

Transaction scheduler and admin retry can generate the same rollback transaction id using `originalTransactionId-RB`. That convention is good, but the reviewed code does not show a strong claim/lock transition such as `PROCESSING` before calling downstream credit.

Risk: Scheduler and manual retry can race. If downstream idempotency is weak, duplicate credit can occur.

### Gap 4: Utility-service idempotency is not visibly enforced before wallet/core posting

Utility has transaction lookup methods, but the reviewed caller methods do not clearly use them before posting to wallet/core.

Risk: Repeated retry with the same reversal id can result in repeated downstream posting unless the deeper wallet system rejects duplicates.

### Gap 5: Missing database uniqueness controls

The reviewed `AirtimeRollbackLog` implementation assumes uniqueness of `(processId, legKey)` but does not visibly declare a database unique constraint. `SuccessDebitLog.transactionId` is also treated as unique by service logic, but uniqueness is not clearly enforced at entity level in the reviewed code.

Risk: duplicate rollback work items can be created under concurrency.

### Gap 6: Direct FxPeer retry endpoint can bypass unified maker-checker

Backoffice has a unified maker-checker reversal desk, but source-specific retry endpoints also exist. Direct execution endpoints should be controlled carefully in production.

Risk: operations users may execute reversal retries outside the central approval/audit path.

### Gap 7: `RECON_REQUIRED` needs an explicit operational workflow

`RECON_REQUIRED` is safer than auto-reversing unknown cases, but backoffice needs a complete workflow to investigate, attach evidence, requery, approve reversal, or mark resolved.

Risk: cases sit unresolved or are handled manually outside system audit.

### Gap 8: Non-airtime FxPeer rollback paths may not be centralized

Rollback-style logic appears in other FxPeer product areas such as offers, orders, and investment orders. These should be assessed and surfaced to the same reversal desk where money movement can fail after partial processing.

Risk: some financial exceptions are invisible to the central operations queue.

## Target reversal principles

1. No reversal without original transaction reference.
2. No reversal without confirmed failed fulfilment or approved manual investigation.
3. Timeout means requery, not reverse.
4. Unknown provider status means hold and investigate, not reverse.
5. Success from provider means no reversal.
6. Partial completion must be handled per leg with explicit evidence.
7. Every reversal must have one immutable idempotency key.
8. Every reversal action must be audited.
9. Maker and checker must be different users.
10. Bulk approval must process each item independently.
11. Scheduler and manual retry must use the same claim/lock/idempotency controls.

## Reversal decision matrix

| Condition | Provider/downstream status | Internal debit status | Decision | Backoffice involvement |
| --- | --- | --- | --- | --- |
| Explicit provider failure | `FAILED` | Debit succeeded | Reverse eligible | Auto or maker-checker based on product/value |
| Provider timeout after submit | Unknown | Debit succeeded | Requery, do not reverse yet | Escalate if stale |
| Connection failure before submit is confirmed | Unknown | Debit may or may not exist | Reconcile request submission state | Manual investigation if unresolved |
| Provider success | `SUCCESS` | Debit succeeded | Do not reverse | Complaint/reconciliation only |
| Provider pending | `PENDING` | Debit succeeded | Keep pending and requery | Escalate after SLA window |
| Provider unreachable | Unknown | Debit succeeded | Retry status enquiry | Manual investigation after threshold |
| Partial provider completion | `PARTIAL` | Some legs succeeded | Per-leg investigation | Maker-checker required |
| Internal debit succeeded, downstream failed | `FAILED` confirmed | Debit succeeded | Reverse debit or compensating legs | Auto or maker-checker based on rules |
| Downstream succeeded, internal ledger update failed | `SUCCESS` | Ledger incomplete | Do not reverse provider; repair ledger | Manual reconciliation |
| High-value failed fulfilment | `FAILED` confirmed | Debit succeeded | Maker-checker reversal | Required |
| Suspicious/conflicting evidence | Any conflicting state | Any | No automatic reversal | Manual investigation |

## Proposed target states

Use a central reversal case state model:

- `DETECTED`
- `STATUS_CONFIRMATION_PENDING`
- `CONFIRMED_FAILED`
- `CONFIRMED_SUCCESS`
- `STATUS_UNKNOWN`
- `PENDING_MAKER_REVIEW`
- `PENDING_CHECKER_APPROVAL`
- `APPROVED`
- `PROCESSING`
- `REVERSED`
- `REJECTED`
- `RETRY_PENDING`
- `MANUAL_INVESTIGATION`
- `FAILED`

Product services can retain product-specific status fields, but the backoffice reversal desk should normalize them into these operational states.

## Proposed central reversal architecture

### Product service ownership

Each product service remains the owner of its domain rules:

- transaction-service owns NIP/local transfer reversal rules
- fxpeer-service owns airtime, VAS, FX, investment, offer, and order domain facts
- utility-service owns wallet/core posting idempotency
- backoffice-service owns approval, visibility, audit, and operator workflow

### Central reversal case view

Backoffice should act as the central operator desk. It should not blindly create money movement. It should only approve or trigger cases where the source service has supplied the required evidence.

Each source service should expose reversal cases with:

- source service
- product
- original transaction id
- end-to-end transaction id
- provider reference
- customer/wallet reference
- amount/currency
- original debit status
- fulfilment status
- provider status check result
- eligibility decision
- current reversal state
- retry count
- last error
- evidence payload, sanitized

### Claim-based processing

Before a scheduler or manual retry executes reversal:

1. Load reversal case by id.
2. Verify status is eligible.
3. Verify fulfilment confirmation is `CONFIRMED_FAILED` or manual override is approved.
4. Atomically claim the case or leg by moving it to `PROCESSING`.
5. Execute reversal using the fixed idempotency key.
6. Persist result and audit.
7. Release to `REVERSED`, `RETRY_PENDING`, `FAILED`, or `MANUAL_INVESTIGATION`.

## Required API changes

### Source services

Each source service should expose:

- `GET /admin/reversals/summary`
- `GET /admin/reversals`
- `GET /admin/reversals/{caseRef}`
- `POST /admin/reversals/{caseRef}/requery-status`
- `POST /admin/reversals/{caseRef}/retry`

Retry must only process a case that is already confirmed eligible.

### Backoffice-service

Backoffice should expose:

- `GET /backoffice/reversals/summary`
- `GET /backoffice/reversals/cases`
- `GET /backoffice/reversals/cases/{source}/{caseRef}`
- `POST /backoffice/reversals/cases/{source}/{caseRef}/requery-status`
- `POST /backoffice/reversals/cases/{source}/{caseRef}/manual-request`
- `POST /backoffice/reversals/bulk/manual-request`
- `POST /backoffice/approvals/{approvalId}/approve`
- `POST /backoffice/approvals/{approvalId}/reject`

Bulk approval must create or process independent child items. One failed item must not hide or roll back other items.

## Maker-checker workflow

1. Source service detects a reversal candidate.
2. Source service performs provider/downstream status enquiry where available.
3. If confirmed failed and eligible for auto reversal, source service can process automatically under idempotency and locking controls.
4. If high-value, conflicting, stale, suspicious, partial, or unknown, source service places it in the central backoffice queue.
5. Maker reviews the case, adds reason/evidence, and submits request.
6. Checker reviews the evidence and approves or rejects.
7. Maker cannot approve their own request.
8. Approval triggers source-service retry through a controlled downstream call.
9. Every action is audited.

## Audit and evidence requirements

Persist the following for every reversal case:

- original transaction id
- end-to-end transaction id
- provider reference
- product and originating service
- original request, sanitized
- original response, sanitized
- failure reason
- response code
- provider status enquiry result
- status enquiry timestamp
- eligibility decision
- maker identity
- checker identity
- approval or rejection timestamp
- reversal reference
- idempotency key
- retry count
- retry history
- before-and-after ledger references
- final status
- correlation id
- audit events

Sensitive values must be masked or encrypted.

## Implementation recommendation

Do not immediately replace the existing reversal flows. Instead, harden them in place while introducing the central control model.

The safest first implementation steps are:

1. Add utility-service idempotency enforcement.
2. Run duplicate audit, then add DB uniqueness for transaction and airtime reversal records.
3. Add `PROCESSING` claim/lock behavior before retry.
4. Add provider status evidence fields and requery flow.
5. Route manual reversal execution through backoffice maker-checker only.

This preserves existing mobile and backoffice integrations while reducing financial and operational risk before go-live.
